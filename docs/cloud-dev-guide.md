# Cloud Development Guide — Cetana Labs (`LAB-000`)

> 📋 **Decision of record:** [`RFC-LAB-000-001`](rfc/RFC-LAB-000-001-cloud-dev-migration.md) — Cloud-Based Development Migration & Environment Classification.
> 🤖 **Agent rules:** [AGENTS.md](../AGENTS.md) (trunk-based, direct commits to `main`).

This runbook explains how to develop the Cetana Labs Control Hub **entirely in the cloud**, with no local machine footprint. It exists because `LAB-000` is a documentation + zero-dependency Python control plane whose automation already executes in GitHub Actions — the local machine was only ever an editor.

---

## 1. Environments

| Environment | Role | When to use |
| :--- | :--- | :--- |
| **Kiro Web** | **Primary** | All current work: docs, Python scripts, dashboard generation, status/sprint governance. Browser-based, agent-native, zero local footprint. |
| **GitHub Codespaces** | Fallback | Reserved for when `LAB-000` grows persistent services (db + server) or needs port-forwarding (see RFC §5). The `.devcontainer/` provisions this reproducibly. |
| **Local IntelliJ + Antigravity** | ❌ Retired for `LAB-000` | Freed for the fullstack initiative that genuinely requires local resources. |

---

## 2. Daily Workflow (Kiro Web)

The entire loop runs in the browser:

```text
edit files  ─▶  /project-validate  ─▶  commit to main  ─▶  push  ─▶  CI deploys
```

1. **Edit** Markdown / Python directly in Kiro Web.
2. **Pre-flight gate** — run the Two-Phase Governance Contract before any status emission or sprint closeout:
   ```bash
   python3 scripts/project_validate.py            # 5-pillar gate (LAB-000)
   python3 scripts/validate_portfolio.py          # portfolio structural integrity
   ```
3. **Commit** directly to `main` with a semantic prefix (per `AGENTS.md` §2):
   ```bash
   git add <files> && git commit -m "docs: <summary>"
   git push
   ```
4. **CI takes over** — GitHub Actions handles the rest (no local action needed):
   - `deploy-pages.yml` rebuilds and publishes the dashboard to GitHub Pages.
   - `project-status-cron.yml` runs the 9:30 AM IST executive broadcast.

## 3. Previewing the Dashboard Without a Local Machine

The dashboard is static HTML generated by a script. To verify a change:

```bash
python3 scripts/generate_dashboard.py    # regenerates docs/index.html
```

Then review by either:
- Opening `docs/index.html` in the Kiro Web file explorer / preview, **or**
- Checking the deployed page after push: <https://agni-eialarasu.github.io/cetana-labs/>

> The Pages deployment is the source of truth for visual QA — a push to `main` reflects live in ~15s.

## 5. Environment Classification (for future projects)

When onboarding a new initiative, classify its `Dev Environment` using the heuristic in [`RFC-LAB-000-001` §4](rfc/RFC-LAB-000-001-cloud-dev-migration.md):

- **☁️ Cloud (default)** — docs, research, static generators, CI-executed automation.
- **💻 Local** — needs persistent local services, hardware (GPU/CV/edge), data-residency, or a heavyweight native toolchain.

Record the result in the project's `STATUS.md` (`Dev Environment` field) and the master registry `Dev Env` column.

---

## 6. Roadmap Note — Evolution to Full Web App (db + server) & RBAC

`LAB-000` is expected to evolve into a full web application with **RBAC-based features** (backlog `BK-007`: role-gated audit trail). This changes *where* the cloud environment runs, **not** the cloud-first decision:

- New services (database, backend server, auth) get declared in `.devcontainer/` — never on the local machine.
- At that point `LAB-000` likely shifts primary from Kiro Web → Codespaces (per RFC §4), staying fully cloud-based.
- The devcontainer is intentionally provisioned now so this transition is additive, not a re-platforming.
